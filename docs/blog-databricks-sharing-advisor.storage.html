Sharing data across teams, platforms, and clouds looks simple until you are several meetings deep in it. Same metastore or different? Read-only or read-write? Does the other side even need raw rows, or just an answer? This post walks through a decision-driven way to pick the right data-sharing architecture the first time, starting with a question most guides skip: what kind of collaboration is this in the first place?

Start one level up: pick the collaboration modality

Most sharing guides jump straight to "which sharing protocol". That skips the more important question. Before choosing a protocol, decide the modality:

  • Direct table sharing — a known consumer needs live, governed access to specific tables or views.
  • Privacy-centric collaboration (clean rooms) — two or more parties want to analyze combined data without any side exposing its raw rows. This is the right answer when sensitive or personal data is involved and an external party is on the other end.
  • Broad publishing (a marketplace) — you want to offer a data or AI-asset product to many, possibly unknown, consumers rather than managing one recipient at a time.
  • AI-asset sharing — the thing being shared is a model, an agent, or unstructured files, or the consumer wants a natural-language question-answering interface over the data instead of the rows themselves.

Only once you have settled the modality does the classic "which protocol" tree apply, and then only to the tabular portion.

The inputs that actually decide the architecture

For direct table sharing, a handful of concrete inputs drive the choice:

  • Topology — Are producer and consumer in the same metastore? Same account? Same region?
  • Consumer platform — the same lakehouse platform, a cloud warehouse, a BI tool, Python/Pandas, a non-native Spark job, dbt, a generic Iceberg REST client, or a JDBC/ODBC SQL client.
  • Access type — read-only, or read-write?
  • Data sensitivity — Public, Internal, Confidential, or Restricted; and does it contain personal data?
  • Freshness and volume — real-time, hourly, daily; small or multi-terabyte.

A decision tree you can actually follow

Evaluate these in order. The first match wins.

  1. Need read-write? Open sharing protocols are read-only. Writable access points to a shared object-store location with separate IAM roles, or governed managed-Iceberg writes over an Iceberg REST catalog.
  2. Same metastore? Grant SELECT directly and let the consumer build views. Zero copy, zero extra compute, live reads.
  3. Consumer wants live SQL over JDBC/ODBC? Point them at a SQL warehouse. Governance applies at query time and no data leaves the platform, but the provider pays the query compute.
  4. Consumer runs an Iceberg engine, or the tables are Iceberg/UniForm? Share over the Iceberg REST catalog. The consumer reads live as native Iceberg, and governance stays central.
  5. Consumer is another workspace on the same platform? Use native platform-to-platform sharing.
  6. Consumer is a warehouse, BI tool, Python, or Spark? Use the matching open-protocol path for that platform.

Read-write and same-metastore short-circuit the tree before platform is even considered, because they change the whole approach.

Match the shared format to the consumer

The format of what you share is a separate, refining choice on top of the protocol:

  • Cross-engine change data capture — modern Iceberg tables carry row lineage and deletion vectors, so a non-native consumer can identify and apply only what changed without full scans or file rewrites. Prefer this over a change feed the consumer's engine has to understand.
  • Semi-structured data — a native variant column type lets logs, API responses, and event payloads live beside relational columns in one governed table, queryable with standard SQL and no schema migration when new fields appear.
  • Delta source, Iceberg reader — a single copy can expose Iceberg metadata over the same files, so an external Iceberg engine reads it live while your platform keeps using it natively. One physical copy, two metadata views, no rewrite.

What good sharing looks like, regardless of path

  • Keep one copy of the data. The best patterns read data in place rather than duplicating it. Iceberg REST sharing, direct grants, and JDBC all avoid a second copy.
  • Govern once, enforce everywhere. Define column masks, row filters, and tag-based policies in the catalog. For engines that query the catalog directly, cross-engine access control means they only ever read authorized rows and columns, without re-implementing the logic per tool.
  • Know what access control does and does not cover. Policies enforced during direct query do not automatically restrict what a share recipient receives. A recipient of a share gets full access to the shared object and applies their own controls. To limit what an external recipient sees, share an aggregated view, a filtered secure view, or only the relevant partitions rather than relying on provider-side masking to travel with the copy.
  • Never share raw personal data externally. For sensitive data going to an external party, prefer a clean room or share aggregates and anonymized products, and require private connectivity plus audit logging.
  • Mind the cost model. Open-protocol and Iceberg REST sharing cost the provider zero compute; the consumer pays for its own queries. A live SQL endpoint flips that — the provider pays per query, so right-size and auto-stop the warehouse. Cross-region reads add egress.

Authentication and networking for external recipients

When the recipient is external and off-platform, two things smooth the path: federated identity, so the recipient authenticates through its own identity provider instead of long-lived tokens, and a managed network gateway, so live access works without hand-crafted firewall rules. For cross-cloud or cross-region sharing, look for one-click connectivity and automatic replication to cut the egress penalty, and for regulated boundaries, purpose-built cross-domain sharing rather than a manual replica.

Where sharing is heading

Zero-copy sharing is expanding beyond tables to materialized views, streaming tables, and AI assets, and the underlying protocol is becoming vendor-neutral and open. Sharing live materialized views lets you publish precomputed aggregates instead of raw rows; sharing streaming tables gives consumers always-fresh data with no duplicate pipeline. The practical takeaway: prefer open, governed, read-in-place sharing over exporting files, and keep the catalog as the single point of governance.

The bottom line

Data sharing does not have to be a fresh judgment call every time. First decide the modality — direct share, clean room, marketplace, or AI-asset sharing. For a direct share, capture the topology, consumer platform, access type, and data sensitivity, then walk the decision tree and refine the format to match the consumer. You will land on an architecture that is governed, cost-aware, and right-sized, whether the consumer is another team in the same catalog or an external partner on a completely different stack.
