Organizations running Databricks on AWS routinely exchange data across teams, accounts, and platforms. A finance team wants a revenue dashboard, a partner wants a product feed, a data science team wants to build models on gold tables, and downstream systems on Snowflake, Power BI, or a custom application need governed access. Often the direction reverses, and the lakehouse must instead consume data from an external source.

The gap between "just share the data" and a safe, cost-efficient production rollout comes down to a small set of decisions: whether the two sides share a Unity Catalog metastore, AWS account, and Region; the consumer platform; whether write access is required; the data classification; the freshness requirement; and, most fundamentally, whether you are the producer sharing data out or the consumer pulling data in. Get those right and the pattern is obvious. Miss one and you are back to unnecessary cross-region egress, sensitive data on the wrong path, or brittle copy pipelines that are expensive to operate.

This guide maps those variables to a recommended architecture, explains the reasoning, and provides copy-paste implementation code for both the producer and consumer sides of 16 patterns. All examples use a fictitious setup (demo_sales catalog, gold_products schema) and placeholder names that you replace with your own.

Section 1: Direction — Are You the Producer or the Consumer?

The single most useful distinction is direction. A producer exposes data to consumers wherever they run; a consumer brings external data into its own lakehouse. The two use different toolkits, so establishing direction first narrows the options quickly.

Two rules underpin every producer decision:

  • Delta Sharing is read-only. The moment someone needs to write, you are no longer sharing — you are running shared storage with carefully scoped IAM roles.
  • JDBC/ODBC and the REST API bill the producer, not the consumer. They run on your SQL Warehouse, so use Serverless with auto-stop and watch the compute. That is the price of zero-copy, always-fresh access.

These patterns collapse into two shapes:

  • Bulk file access — Delta Sharing (all flavors), Delta UniForm + Iceberg REST, and shared S3 hand the other side the underlying Parquet/Delta files, read via short-lived pre-signed URLs. The provider spends zero compute.
  • Live query — JDBC/ODBC and the REST API run queries through a SQL Warehouse. The consumer always sees current data and needs no copy, but the provider pays the compute for every query.

For the bulk-file shape when the consumer is not on Databricks there is a protocol choice. Delta Sharing is Databricks' own protocol; Delta UniForm + the Unity Catalog Iceberg REST catalog publishes an Apache Iceberg metadata view over the same Parquet, so any Iceberg-native engine (Snowflake, Trino, Flink, Athena) reads it as a native Iceberg table. Best for: reach for UniForm when the consumer wants open-table-format interop or one manifest to serve many engines; reach for Delta Sharing when they are happy speaking the Delta Sharing protocol. Both are zero-copy and UC-governed.

Section 3: Consume — Which Pattern Brings Data In?

When your lakehouse is the consumer, you have five options. In nearly all cases, reading the data in place is preferable to copying it in.

You're receiving from…Recommended architectureWhy
Another Databricks account/metastoreMount the D2D share as a catalogCREATE CATALOG … USING SHARE — the data stays in the provider's S3, you query it live
Snowflake, Postgres, Redshift, MySQL, BigQueryLakehouse FederationRegister the source as a foreign catalog and query it in place — no ingestion pipeline
Another catalog — AWS Glue / Hive MetastoreCatalog FederationFederate the whole metastore into UC as a foreign catalog; read Glue-registered tables via the three-level namespace

Federation is often the most valuable option. When a partner runs a Snowflake or PostgreSQL warehouse, the common instinct is to build an ingestion pipeline: schedule a job, land the data in bronze, reconcile schema drift, and operate it indefinitely. Federation avoids that entirely — you register the external database as a foreign catalog in Unity Catalog and query its tables live, in place, governed by the same permissions as your own tables.

Federation comes in two flavors:

  • Lakehouse Federation connects to a query engine (Snowflake, Postgres, Redshift, BigQuery) over a JDBC-style CONNECTION and pushes queries down to it.
  • Catalog Federation connects to a metastore — most commonly an AWS Glue Data Catalog or Hive Metastore — and surfaces every registered table under a single UC foreign catalog.

The consumer's default should be "query in place," not "copy in." D2D shares, Lakehouse Federation, and external-location reads all leave the data where it lives. Introduce a copy-based ingestion pipeline only when you need historical snapshots or when query volume makes live federation too chatty. Ingestion is the exception you justify, not the reflex you start with.

Section 4: Secure — How Do I Keep Sensitive Data on the Right Path?

Picking the pattern is only half the job. Turning a whiteboard box into a safe production rollout is the other half, and it is where most designs quietly go wrong.

Layer 1: Prerequisites and access as code

Do account-level groups exist yet? Is the consumer a service principal that needs OAuth credentials — using OAuth machine-to-machine rather than a long-lived personal token? Is the consumer external, requiring a Unity Catalog RECIPIENT and a securely transmitted activation link? In a governed estate, access is as-code: open a Terraform PR to add the consumer's service account (never an individual) to the data product's consumer group; a compliance/classification gate and the domain owner's approval must pass before it goes live. Verify the metastore relationship per consumer — run SELECT current_metastore() on both sides rather than assuming from the account boundary.

Layer 2: Environment matching

Prod talks to Prod, QA to QA, Dev to Dev. Delta Sharing recipients and IP allowlists are environment-scoped, and cross-environment access (Prod↔QA) is blocked by design, so a lower environment can never reach production data, whether over the sharing path or the JDBC fallback.

Layer 3: Security that scales with sensitivity

PII calls for dynamic views with column masking (is_account_group_member) and tagged PII columns. Confidential or restricted data adds audit logging, PrivateLink (no public internet), and a mandatory security-team review. For external recipients, harden the bearer token: set an expiration, rotate on a schedule, and restrict access with an IP allowlist. One hard line: PII + external consumer = high risk. Share only aggregated or anonymized data, never raw PII tables. When two parties genuinely need to compute on combined sensitive data, that is a job for a Clean Room, not a share.

Layer 4: Cost, before the invoice

Cross-region sharing incurs S3 egress (typically ~$0.01–0.02/GB depending on the region pair); at high volume, replicate to the consumer's region instead of paying egress on every read. Remember which shape you picked: Delta Sharing reads cost the provider zero compute, while JDBC/ODBC and the REST API bill the provider's SQL Warehouse per query. For large API result sets, use the EXTERNAL_LINKS disposition (pre-signed URLs) rather than inlining megabytes of JSON.

Conclusion: Start Sharing

Choosing how to share data on Databricks on AWS is fundamentally a decision tree: a small set of inputs — direction, metastore relationship, consumer platform, access mode, data classification, and freshness — determines the right architecture. To apply the framework:

  1. Start from the decision tree to identify your pattern.
  2. Use the one-page cheat sheet to confirm its trade-offs.
  3. Copy the corresponding provider and consumer code from the appendix, replacing the placeholder names with your own.

In every case, prefer the highest zero-copy, Unity Catalog–governed option before resorting to a copy-based pipeline.
